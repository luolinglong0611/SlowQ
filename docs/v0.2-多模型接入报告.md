## 1. 目标与硬约束

目标来自实现需求书（在项目目录之外，不随仓库分发）。本轮的验收口径不是
"能跑出中文"，而是每个模型都能在 FP32 上与官方实现逐项对齐。

需求书里几条约束贯穿所有改动，本轮没有为了赶进度绕过任何一条：

| 约束 | 本轮的执行情况 |
| --- | --- |
| 优先级：计算正确 > 完整可用 > 代码可读 > 性能优化 | 每个模型都是先过参考数值比较，再谈功能测试与计时 |
| 容差必须在测量**之前**声明 | 跨实现的 logits / hidden / weights 三组门限沿用 v0.1 原值，只新增向量一组（`rel_l2 1e-3` / `max_abs 1e-3`）；集成测试用的内部一致性门限（`rel_l2 1e-5` / `max_abs 1e-3`）也是 v0.1 的原值，本轮只是从 `test_integration_real_model.py` 挪进共享的 `tests/real_models.py` |
| 不得凭"生成了一句合理的话"判定正确 | 三个任务都比较 logits / hidden states / 向量的数值，图文任务另外逐段比 pixel 张量、视觉塔输出、connector 输出与融合位置 |
| 运行时不得依赖 torch / transformers / onnxruntime / llama.cpp / 远程 API | `tests/test_dependency_boundary.py` 6 项守卫，子进程导入全部运行时模块后检查 `sys.modules` |
| 转换后必须完全离线 | 8 个模型各有一条阻断 socket 后跑 `inspect` 与对应任务命令的测试 |
| 权重与大产物不入 Git | `models/`、`artifacts/` 保持忽略；参考图像由 NumPy 侧生成、参考侧按 sha256 校验，不入库 |
| 不破坏用户已有模型目录 | 转换器仍是暂存式安装、默认拒绝覆盖非空目录；v0.1 转好的 Qwen3-0.6B **未被重新转换**，直接用来验证读旧 manifest |

## 2. 实施顺序

顺序不是按模型大小排的，而是按**每步引入多少新的架构变量**排的：先在同一家族里
放大规模，再换家族，再加任务，最后加模态。

| 阶段 | 内容 | 引入的新变量 |
| --- | --- | --- |
| 1 | 最小模型/任务抽象重构 | `family` 与 `task` 两条轴；家族规则表取代按模型名分支 |
| 2 | SmolLM2-135M / 360M-Instruct | 第二个家族 llama：无 Q/K norm、bias 全部从 config 读、不同 eps 与 rope_theta |
| 3 | Qwen2.5-0.5B-Instruct / Coder | 第三个家族 qwen2：硬编码的 QKV bias、`sliding_window` 存在但未启用 |
| 4 | Qwen3-1.7B | 同家族放大规模：2 个 safetensors 分片、6.4 GiB 权重、tied weights |
| 5 | Qwen3-Embedding-0.6B | 第二个任务：无 lm_head、pooling、query 前缀、按文本长度分配缓存 |
| 6 | SmolVLM-256M-Instruct | 第三个任务与第四个家族：视觉塔、图像预处理、特征注入、Pillow extra |
| 7 | `validate_reference.py` 重构 | 抽样层与抽样权重按家族/任务参数化；artifact 按模型分目录；格式升到 3 |
| 8 | 集成测试、文档与状态矩阵 | 四个集成模块按 manifest 任务过滤；5 篇文档改写 + 新增 2 篇 |

阶段 7 在阶段 6 之后：重构验证工具时手上已经有一个真正异构的任务（图文），
所以抽样层、抽样权重与 artifact 布局的参数化不是照着几个同构模型做的。

## 3. 关键设计决策

### 3.1 family 与 task 拆成两条正交的轴

这是本轮最核心的一条。`family` 由 `config.json` 的 `model_type` 决定，回答
"这些权重按什么规则计算"；`task` 由转换后目录的 manifest 记录，回答
"这份目录拿来做什么"。两者都不能从对方推出来：

* **task 推不出来。** `Qwen/Qwen3-Embedding-0.6B` 的 `model_type` 是 `qwen3`、
  `architectures` 是 `["Qwen3ForCausalLM"]`，这两个字段与聊天模型取值一致。
  整个 `config.json` 确实不同（`vocab_size` 151669 vs 151936、`eos_token_id`
  151643 vs 151645、`max_position_embeddings` 32768 vs 40960），
  但没有一项能可靠地指示任务。按架构名字分派入口的加载器会把向量模型当生成模型建起来，
  然后在第一次前向时缺 `lm_head` 失败——或者更糟，用一个不该存在的输出投影
  算出一个看起来正常的向量。
* **family 也推不出来。** SmolVLM 内嵌的文本 config 的 `architectures` 里写着
  `VLlama3ForCausalLM`，而官方 `Idefics3Model` 是按 `model_type` 经
  `AutoModel.from_config` 分派的，根本不看 `architectures`。

所以 family 读 config、task 读 manifest，两个方向都不猜。

### 3.2 家族规则表取代"按模型名分支"

v0.1 的代码里有若干处写死了 Qwen3 的事实（有 Q/K RMSNorm、QKV 有 bias、
head_dim 可以推导）。本轮把它们全部收敛到 `config.py` 的 `TEXT_FAMILIES`，
依据是 transformers 4.51.3 的官方 modelling 代码，不是模型名字。规则表本身在
[模型支持 · 架构家族事实](models.md#架构家族事实)，这里只记三条容易写错的：

* **qwen3 的 `head_dim` 必须显式存在。** Qwen3-0.6B 的 `hidden_size=1024`、
  16 heads，但 `head_dim=128`，Q/K/V 投影输出 `16×128 = 2048`，比 hidden_size 大一倍。
  按 `hidden_size / heads` 推导会直接算错形状，所以缺失时报 `ConfigError` 而不是回退。
  直接后果：两个 Qwen3 的 KV cache 都是 224.0 KiB/token，尽管 hidden_size 差一倍。
* **qwen2 的三条 bias 规则是硬编码在 `Qwen2Attention.__init__` 里的**，config 里没有字段：
  Q/K/V 恒有 bias、O 投影恒无、MLP 恒无。写成 `config:attention_bias` 会让
  Qwen2.5 少算或多算 bias，而这类错误的表现是"数值差一点"，不是崩溃。
* **sliding window 按实际启用状态判断。** 两个 Qwen2.5-0.5B checkpoint 的 config 里都有
  `sliding_window: 32768` 且 `use_sliding_window: false`。既不因为字段存在就拒绝加载，
  也不会把真正启用的滑动窗口当成全注意力算。

### 3.3 manifest `format_version` 2，同时继续读 1

版本 2 增加 `task` 与 `model_family` 两个必填键；版本 1（只有 v0.1 写过）仍可读，
缺键时按 v0.1 的唯一可能取值处理为文本生成——这不是猜，v0.1 只转换过 Qwen3 causal LM。
其他版本号被拒绝，不静默降级。

带来的直接好处：v0.1 转好的 2.2 GiB Qwen3-0.6B 目录**不需要重新转换**，
它同时也是"读旧格式"这条路径的真实测试样本（`models.md` 的来源表里它是唯一的 v1）。

### 3.4 转换器的任务识别读文件证据，不读仓库名

`--task auto` 的判据是目录里有什么文件：sentence-transformers 导出的三个标记文件
（`modules.json`、`config_sentence_transformers.json`、`1_Pooling/config.json`）表示向量模型；
嵌套 `vision_config` 加 processor 文件表示图文模型。**三个标记文件只出现一部分时报错**，
不取多数票。显式指定 `--task` 时仍会与文件证据交叉校验，所以"用户说是生成模型、
目录里却有 pooling 配置"会被拦下来。

每个 repo 的 commit 由转换器当时解析并写入 manifest，不再套用 v0.1 为 Qwen3-0.6B
固定的那个 revision。

### 3.5 参考验证协议按家族与任务参数化

v0.1 的抓取点固定在 q_norm 与第 27 层，那是 Qwen3-0.6B 的形状。本轮改为：

* 抽样层取 `(0, L//2, L-1)`，逐模型算出来（Qwen3 是 0/14/27，SmolLM2-360M 是 0/16/31）；
* 抽样权重张量跟着家族走：qwen3 取 `q_norm`/`k_norm`，qwen2 取 `q_proj.bias`，llama 两者都不取；
* artifact 目录按模型名分开（`artifacts/validation/<模型目录名>/`），验证第二个模型不会覆盖第一个；
* `ARCHITECTURE_FIELDS` 里每一项都由参考侧用官方 modelling 代码自己的表达式
  从原始 `config.json` 复述一遍，两边一致才开始比数值——架构层面的分歧不会被数值门限掩盖；
* 三进程协议（numpy → ref → compare）保留，`compare` 不给假 PASS：
  缺文件返回非零退出码，形状/dtype/有限性/协议不匹配一律拒绝。

## 4. 三个任务的接入要点

### 4.1 文本生成（6 个模型，3 个家族）

一份 decoder 实现跑通 qwen3 / qwen2 / llama。差异全部落在规则表与权重清单
（`required_text_tensors`）里，前向代码没有家族分支。GQA 不物化 `repeat_kv`，
而是把 query head 折进 batch 轴；group size 为 1 时退化成 MHA——SmolVLM 的视觉塔
正是用这条路径跑 `mask=None` 的全连接注意力。

SmolLM2 两个 checkpoint 除家族规则外还有几处与 Qwen 不同：`rms_norm_eps` 是 `1e-5`
而不是 `1e-6`，`rope_theta` 是 `100000` 而不是 `1000000`，词表 49152，
目录里多一个 `special_tokens_map.json`。这些都从 config 读，没有写死。

### 4.2 文本向量（Qwen3-Embedding-0.6B）

新模块 `src/slowq/embedding.py`。四个**静默出错点**是这一节的重点，
每一个都与官方 snippet 逐项核对过：

| 环节 | 官方做法 | 搞错的后果 |
| --- | --- | --- |
| `add_special_tokens` | `True`，post-processor 追加 `<|fim_middle|>`（id 151643） | 池化位置错一个 token，向量整体不同，但看起来仍然"正常" |
| pooling | 最后一个有效 token 的 final hidden state | 平均池化会给出一个可用但不同的向量 |
| attention | 保留官方因果注意力，**不是**双向 | 改成双向是常见误解，数值全错 |
| lm_head | **不做**全词表投影 | 输出维度会变成 151669 而不是 1024 |

另外两条工程决定：KV cache 按当前文本长度分配而不是按 `max_length`（默认 8192）预分配，
否则一句 20 token 的话要白分配 1792 MiB（实测该 checkpoint 是 224 KiB/token，
20 token 只需 4.4 MiB）；超过 `max_length` 时报错而不截断，
因为截断后的向量与短输入的向量不同，返回它等于给一个静默的错答案。

"不做全词表投影"由一条消融测试守住：把 `output_projection` 换成抛异常的桩，
编码仍然成功。

### 4.3 图文生成（SmolVLM-256M-Instruct）

新模块 `src/slowq/vlm.py`（1403 行，是本项目最大的单个源码文件）。这是**真正的图像条件生成**，
不是拿里面的文本塔跑纯文本。三件容易低估的事：

* **"只支持一张图"不等于只有一个 crop。** 官方 `do_image_splitting: true` 会把图
  resize 到最长边 2048、再向上取整到 512 的倍数，切成 rows×cols 个 512×512 crop
  **再加 1 个全局帧**。实测：300×1200 的图切成 1×4 共 5 帧、320 个 image token、
  prompt 360 token；400×800 的图切成 2×4 共 9 帧、576 个 image token、prompt 612 token。
  所以图片尺寸会影响整个请求的耗时，不只是预处理那一步。
* **视觉塔与文本塔是两套东西。** LayerNorm（weight + bias）而不是 RMSNorm，
  fc1/fc2 + `gelu_pytorch_tanh` 而不是 SwiGLU，q/k/v/out_proj 四个投影都带 bias，
  全连接**非因果**注意力，位置来自学习到的 `position_embedding.weight`，没有 RoPE。
  复用文本塔的算子会静默算错。
* **`image_seq_len = 64` 来自 pixel shuffle。** `(512/16)² / scale_factor² = 1024/16`，
  connector 是 pixel shuffle 之后的 `modality_projection.proj`（12288 → 576，`bias=False`）。

Pillow 是可选 extra（`slowq[vision]`），且只在真正读图时导入——
`import slowq.vlm` 本身不导入它，纯文本安装不会被强制装上视觉依赖。
这条由依赖边界测试守着。

图像读不到、占位符数量对不上、扩展后超过 `max_context`，都报错并说明原因；
一次请求只接受一张图，第二张报错。

## 5. 过程中踩到的坑（可复用的部分）

| 现象 | 原因与处理 |
| --- | --- |
| 首轮性能数据自相矛盾：权重更小的 SmolLM2-360M 冷启动首次前向 5.58 s，SmolLM2-135M 只有 1.68 s | 冷启动被操作系统页缓存状态支配，不适合横向比较。已在 [benchmarks.md](benchmarks.md) 里明确标注，并把 8 token 的 `full` 一行从吞吐表里去掉 |
| 六个模型串在同一个 shell 循环里测，Qwen3-1.7B 的 512-token prefill 是 4262 / 8004 ms | 同进程连续测多个模型会互相污染，且当时还有集成测试在跑。改成**每模型一个独立进程**重测，同一项变成 2002 / 2162 ms |
| `grep -c "^def test_"` 数出来的测试数与真实收集数不符（`test_vlm.py` 49 vs 75） | 参数化与缩进会让 grep 少数或漏数。文档里的测试数一律改用 `pytest --collect-only` 的结果 |
| macOS 传到 Linux 的源码里出现 `._ops.py`，AST 扫描报 UnicodeDecodeError | macOS 的 `tar` 默认写 AppleDouble 元数据，它们以 `.py` 结尾会被当源码读。传源码要 `COPYFILE_DISABLE=1` |
| 想验证"截断分片报出自己的错误"，却先撞上 tied 权重守卫 | 截断长度要选在**让 tied 自检也能通过**的位置（`lm_head.weight` 与 `model.embed_tokens.weight` 都还在文件里），否则看到的是另一条失败路径 |
| v0.1 的断言"Qwen3 一定有 Q/K RMSNorm"在换家族后变成假命题 | 没有删掉这条检查，而是改写成"qwen3 家族有、qwen2 与 llama 家族没有"，负向用例保留 |
| 文档收尾时复核数字，发现四处对不上 | 见下 |

最后一条的四处，都是在文档写完后**用命令逐条复核**时发现的，不是读者指出的：

* `embedding.py` 的注释写"按 8192 token 预分配会占 235 MiB"。实测该 checkpoint 是
  224 KiB/token，8192 token 是 **1792 MiB**；235 MB 其实是 1024 token 的量。注释与本报告都已改正。
* SmolVLM 的 `prompt token 360 / 612` 用文档里给的复现命令跑不出来（得到 356）。
  原因是两个样例的问题文本与 system 设置**并不相同**，它们沿用参考验证抓取里的两条样例，
  而抓取用的问题没有写进性能文档。补上 question / system 后 360 与 612 逐字复现。
* 向量模型的编码耗时表里，"21 token / 70.7 ms"那一行是**两条 21 token 样例的平均**
  （英文 69.7 ms 与中文 71.7 ms），却在样例列只写了英文那条。已拆成两行分别列出。
* 5 处文档都写着"最差 rel_l2 是门限的 1/38 ~ 1/625，最差 max_abs 是 1/3 ~ 1/5000"，
  还断言最差值"不在 logits 上"。从 8 份 `compare.log` 的 860 行数值表按**每个张量自己
  适用的门限**重算，实际是 **rel_l2 1/37 ~ 1/394、max_abs 1/3 ~ 1/202**，而且最差 rel_l2
  有 3 个模型就在 logits 上。`1/625` 与 `1/5000` 这两个上界在日志里根本不存在。

第四条最说明问题：`models.md` 那张逐模型最差值表**每一格都对**（16 个数值与张量名逐个
核对过），错的只是紧跟在表格下面那句人工归纳的范围。**表格正确不代表由它归纳出的结论正确**——
凡是"最值 / 范围 / 占比"这类二次计算的句子，都要回到原始数据重算，不能从表格里目测。

教训是同一条：**写进文档的每个数字都要能被文档里给出的命令或仓库里的 artifact 重新算出来**，
包括"这个数是哪条输入测出来的"。

## 6. 验证结果

命令与原始输出在 [validation.md](validation.md)，逐模型数值在

下表是发布前修复那一轮（2026-10-21）逐模型**单独设置** `SLOWQ_MODEL_DIR` 的实测结果，
耗时是 pytest 自己报告的会话时长：

| 模型 | 结果 | 该轮耗时 |
| --- | --- | --- |
| SmolLM2-135M-Instruct | 26 passed, 36 skipped | 6.84 s |
| Qwen3-Embedding-0.6B | 25 passed, 37 skipped | 12.07 s |
| SmolLM2-360M-Instruct | 26 passed, 36 skipped | 14.62 s |
| Qwen2.5-Coder-0.5B-Instruct | 26 passed, 36 skipped | 15.48 s |
| Qwen3-0.6B | 27 passed, 35 skipped | 19.18 s |

合计 **208 passed, 0 failed**。Qwen3-0.6B 多出的 1 项是 v0.1 遗留的固定输出回归，
它显式检查 checkpoint 来源；Qwen3-Embedding-0.6B 少 1 项是因为参考比较里没有

Qwen3-1.7B 那 4036.71 s 与宿主机内存压力相符：它的权重目录是 6.4 GiB，
测量时 swap 已用 5.9–7.4 GiB，峰值 RSS 涨到 6.43 GiB ≈ 权重整体积。
需要说清楚的是，权重由 `np.load(..., mmap_mode="r")` 建立只读映射，
**页面驻留由操作系统管理**——映射本身不保证 6.4 GiB 全部常驻，RSS 本来可以远低于此；
峰值 RSS 包含进程的其他内存，不能单独证明权重页反复调入调出。另有两项耗时观测：
`sys` 845 s 是 `user` 126 s 的 6.7 倍；real 4037 s，而 `user + sys` 为 971 s，
约为墙钟时间的 24%。这个比例不是整机 CPU 利用率，时间差额也不能全部归为 I/O 等待。
它**26 passed、0 failed，跑完了**，没有为此缩短测试或放宽断言。
接入批次记录到同一套测试约 62.7 s，这是历史观测。上一轮只留下“约 10 分钟、
6 passed 后中断”的不完整结果；本轮 `test_greedy_generation_is_deterministic`
耗时 630.66 s。时间量级接近，本身不能证明中断位置或异常耗时原因。

**内存压力仍是待验证的解释，尚未排除其他性能因素**：
资源充足环境下的对照测量还没有做过。完整诊断见
[测试与数值验证](validation.md#qwen3-17b-的异常耗时与宿主机内存压力相符)。

### 6.3 官方参考数值比较

三进程协议，参考环境 `transformers 4.51.3` / `torch 2.14.1` / eager attention / FP32 / CPU /
线程 4（SmolVLM 为 8）。8 个模型全部 `PASS`，最差 rel_l2 落在门限的 1/37 ~ 1/394，
最差 max_abs 落在门限的 1/3 ~ 1/202。**最差 max_abs 八个模型都在深层 hidden states 上**；
最差 rel_l2 有 3 个模型在 logits 上（Qwen2.5-0.5B、Qwen3-0.6B、SmolLM2-135M），
SmolVLM 在视觉塔输出上，其余在 hidden states 上；所有 greedy argmax 位置两侧完全一致。

门限自 v0.1 起没有为任何失败样例放宽过。逐模型最差值与张量名见
[模型支持 · 参考数值验证结果](models.md#参考数值验证结果)。

发布前修复改了向量的参考抓取流程（第 7 节的问题 3），所以向量那一侧的证据是
**重新抓的**，不是引用旧 `compare.log`：NumPy 侧与官方参考侧都离线重跑一遍，
`embedding_input_format` 两边都是 2，8 条样例逐条 `input=ok pooled=ok`，
`PASS: 82 tensors`；重抓后最差 rel_l2 4.935e-06、hidden max_abs 7.629e-04、
vector max_abs 5.364e-07，都在门限内且门限没动。生成侧没有受影响——
SmolLM2-135M 重抓后 `slowq.npz` 与旧的逐字节相同，仍是 `PASS: 116 tensors`，
它的抓取配置里也没有 `embedding_input_format` 这个键。

## 8. 复现路径

```bash
# 0. 环境
python3 -m venv .venv && source .venv/bin/activate
python -m pip install -e ".[dev]"          # 快速测试只需要 pytest

# 1. 快速测试：无网络、无真实权重
python -m pytest -m "not integration" -q

# 2. 转换（每个模型一次；不要覆盖已有目录）
python tools/convert_model.py --repo HuggingFaceTB/SmolLM2-135M-Instruct \
    --out models/SmolLM2-135M-Instruct-slowq

# 3. 真实权重集成测试：manifest 里的任务决定哪些模块运行
SLOWQ_MODEL_DIR=models/Qwen3-Embedding-0.6B-slowq python -m pytest -m integration -q

# 4. 参考数值比较：三个独立进程，按 numpy → ref → compare 顺序
python -m pip install -e ".[ref]"          # 只有 ref 子命令需要 torch/transformers
M=models/SmolVLM-256M-Instruct-slowq
H=models/SmolVLM-256M-Instruct-slowq-hf/HuggingFaceTB--SmolVLM-256M-Instruct/7e3e67edbbed1bf9888184d9df282b700a323964
python tools/validate_reference.py numpy   --model "$M" --max-context 1024 --prefill-chunk-size 100
python tools/validate_reference.py ref     --model "$M" --hf-dir "$H" --threads 8
python tools/validate_reference.py compare --model "$M"

# 5. 任务命令（SmolVLM 还需要 pip install -e ".[vision]"）
python -m slowq generate --model models/Qwen3-0.6B-slowq --prompt "用一句话解释什么是 KV cache"
python -m slowq embed    --model models/Qwen3-Embedding-0.6B-slowq \
    --query "太阳系里哪颗行星的卫星最多？" --document "土星已确认 146 颗卫星。" --json
python -m slowq vlm      --model models/SmolVLM-256M-Instruct-slowq \
    --image picture.png --question "图里有哪些形状？" --json

# 6. 发布前修复的回归测试（第 6.6 节改动集中的四个文件）
python -m pytest tests/test_embedding.py tests/test_model.py \
    tests/test_vlm.py tests/test_validate_reference.py -q
# -> 发布前修复轮 255 passed（35 + 48 + 81 + 91），验证工具修复轮 275 passed（35 + 48 + 81 + 111）

# 7. 干净环境安装验证（第 6.7 节；不要装进开发用的 .venv）
#    注意：仓库里若已有 setuptools 留下的 build/，先移走再打 wheel，
#    否则会把 build/lib 里的陈旧源码打进去（本轮就差点把已删除的
#    padding_attention_mask 重新发布出去）。
python -m pip wheel . --no-deps --no-build-isolation -w /tmp/slowq_dist
python3 -m venv /tmp/slowq_clean
/tmp/slowq_clean/bin/python -m pip install "/tmp/slowq_dist/slowq-0.2.0-py3-none-any.whl[dev]"
/tmp/slowq_clean/bin/python -m pytest -m "not integration" -q

# 8. 验证工具修复的负向验证（第 6.8 节）：一条命令重跑全部
#    脚本只在 /tmp 里生成撤回变体与被删字段的 artifact 副本，仓库源码不受影响。
#    该目录在 artifacts/ 下，被 .gitignore 忽略，不随仓库分发。
zsh artifacts/repair-review-20261021/negative-validation/run_all.sh

# 9. 对既有 artifact 重新比较（不是重抓）：8 份都应退出码 0
for d in artifacts/validation/*/; do m=$(basename "$d"); \
    python tools/validate_reference.py compare --model "models/$m"; done
# -> 6 x "PASS: 116 tensors" + 2 x "PASS: 82 tensors"，合计 860
```

文本生成模型的第 4 步用默认参数即可
（`--max-context 512 --prefill-chunk-size 8 --decode-steps 3`）；
SmolVLM 的 prompt 展开后是 612 token，必须放大 `--max-context`。
`--artifacts` 缺省时由 `--model` 推导，所以验证第二个模型不会覆盖第一个的抓取。
