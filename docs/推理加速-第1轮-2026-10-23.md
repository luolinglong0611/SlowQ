## 2. 优化 1 + 2：删掉 prefill 与 decode 里的冗余计算

### 2.1 各自省掉了什么工作

**优化 1：非末 prefill chunk 不再做词表投影。**
`CausalLMModel.prefill()` 原来对每个 chunk 都调 `forward()`，但生成只从最后一个 token
采样，所以只有末 chunk 的 logits 被读过。现在非末 chunk 走 `encode()`（decoder stack +
KV 写入，不碰 `lm_head`），末 chunk 走 `forward()`。**被观测到的**投影次数从 4 降到
1（512 token / `chunk_size=128`），计数来自一个带深度守卫的 instrumented spy，同时统计
`forward` 与 `encode`，不是从 `length // chunk_size` 推的。

**优化 2a：`sigmoid` 改写成 `exp(-|x|)` 的无分支形式。**
原来的写法用两次布尔掩码索引，要在 MLP 的 `[T, intermediate_size]` 激活上做四次 gather。
这一项是本轮 prefill 加速的**主要来源**，实测见 §2.3。

**优化 2b：单 token decode 跳过恒为全零的 causal mask。**
在「完整因果注意力 + 只读有效 KV 前缀」下，一 token 前向的因果三角已经覆盖全部缓存键，
`causal_attention_mask` 返回的是全零 `[1, 1, 1, S]`；FP32 下加零是恒等操作，而这个 mask
建一次却被每一层消费一次。触发条件是**推导出来的**，不是假设的：掩码元素
`(i, j)` 为零当且仅当 `j <= offset + i` 对所有 `j < offset + num_tokens` 成立，化简即
`num_tokens <= 1`，所以它恰好在单 token 时触发，绝不会误伤还有自己三角的 chunk。

### 2.2 正确性怎么验的

`sigmoid` 的比较里有两个坑，分开记：

1. `nan` 有多种位模式，`nan / nan` 可以落在与 `exp(nan)` 不同的 payload 上，
   所以直接比字节会在两边同样都是 NaN 的地方报差异。做法是先用
   `np.array_equal(..., equal_nan=True)` 比，再只在两边都非 NaN 的位置比字节。
   **因此「NaN 位置一致」与「NaN 位模式一致」是两个不同的断言**，本报告只声称前者；
   探针把它作为一条 note 单独打出来，不并入逐位结论。
2. 逐位结论只能来自原始数组的比较。日志里打印的聚合误差（rel_l2、max_abs）
   两侧相同**不能**证明张量逐位相同——聚合量相等允许元素级差异互相抵消。

`softmax` 明确不得写入入参——否则调用方会在「pre-softmax」这个名字下拿到概率，
而且能过所有数值检查。缓冲区所有权写死在 docstring 里。

### 2.4 两项改动的归因：prefill 的加速不是优化 1 带来的

`engine_prefill` 的加速是**优化 1 + 优化 2 之和**，两者极不均匀，所以必须拆开归因，
不能把整个加速记在任何一项头上。

拆不开的原因要说清楚：`raw_prefill_full` 两棵树都只投影 1 次，它的差值确实只含优化 2，
但它与引擎的分块循环**不是同一条路径形状**（一次全长 attention vs 四次逐渐变长的），
所以它的绝对毫秒数不能直接从引擎的绝对毫秒数里减掉——只有比值能比。

`projection_probe.py` 直接补上缺的那一项：`forward` 就是 `encode` 加一次
`output_projection(hidden[-1])`（`model.py:390-398`），所以在同一棵树、同一批 id、
同一个进程里**成对**计时再相减，得到的就是一次投影的净代价，权重、内存状态、
进程全部固定。
`output_projection` 在两棵树之间**逐字节相同**（已 diff 核对），所以在 opt
树上测到的投影代价可以直接用来给 base 树当初多做的那几次定价。

**探针自身的精度**：一次投影的代价与块长无关（永远是 `[1, hidden] × [hidden, vocab]`），
所以 128 / 256 / 512
三行是**同一个量的三次独立测量**，它们的离散度就是这个探针的误差棒。本批 105
对成对样本里有 **25 对为负**（23.8%，分布在 5/5 个模型上），最差的一对是 Qwen3-1.7B 在
128 token 上的 **-13419 ms**。而 `forward` 就是 `encode` 加一次真实存在的投影，
**成对差值不可能为负**——出现负数只说明模型在成对计时的两半之间被换出了内存。
所以**任何单次观测都不能用**，能用的是中位数；而中位数为负的那一行**整行作废**（下表标
`作废`，且不进「三者中位」）。

**其中 8 对负值落在中位数仍为正、
因而没有被标 `作废` 的行里。**所以「没标作废」的准确含义
是**这一格的 7 对里中位数为正**，不是「这一格测量干净」。
这也是下面那个占比只能当区间读、且必须连着跨批次的重复性一起看的原因。

#### 两条独立路线给优化 2 定价，互相核对

路线 A：`引擎实测省下 − 探针测到的 3 次投影` = 优化 2。
路线 B：`raw_prefill_full` 的 base−opt 差值 = 优化 2（两棵树都只投影 1 次）。
两条路线用的输入不同、路径形状不同、连测量时刻都不同，所以它们对得上才是真的对得上。
`相差` 一列大到与下面优化 5 那节的跨进程离散度同量级，就说明三项测量里有一项是错的。

**整行跳过的两种情况**（跳过而不是印一个数出来）：
- 探针 512 tok 的成对差值中位数 ≤ 0 —— 路线 A 会**减去一个负数**，把优化 1
  的功劳算到优化 2 头上，越脏的探针算出来优化 2 越大。
- `raw_prefill_full` 的自检不过（上面那张表的 `自检` 列 >1.15×）—— 路线 B
  整个是机器状态，不是代码。

**跳过 1 个模型：Qwen3-1.7B（探针 512 tok 中位数 -2963.35 ms ≤ 0）。
**被跳过不等于「相差很小所以省略」，
而是**这张交叉核对表对它无法成立**——两条路线各有一个输入已经作废。
上面「一次词表投影的净代价」表里标 `作废` 的行、「整块 prefill」表里标 `待重测` 的行，
对应的就是这里的这几个模型；三张表少的是同一批行。

两条路线最大相差 **17.9%**，最小 4.3%（4 个模型；判据是 ≤15%，
即报告其余各处「同一件事的两次独立测量」用的同一个门限）。**交叉核对没有通过**：最差那
17.9% 超过了 15%，说明这三项测量（引擎差值、探针投影、`raw_prefill_full` 差值）
里**至少有一项在这一批里不可用**。所以「省下的大部分来自优化
2」这一句在本批数据上**不能由这张表支撑**——它只能由上面那张「优化 1 占比」表支撑，
而那张表给出的占比本来就在个位数百分比以下，两条路线一致与否并不改变那个量级。

**归因结论：**

- 上面那个占比区间的下界是 **0.22%**，本批**不是负数**——成对差值中位数为负的行已整行
  `作废`，不进这个区间。本批标 `作废` 的有：Qwen3-1.7B（128、256、512 tok
  的成对差值中位数为负）。作废的理由**不是**「这个量低于探针自己的分辨率」：`forward` =
  `encode` + 一次真实存在的投影，成对差值为负在算术上不可能，
  只能是**测量无效**（模型在成对计时的两半之间被换出了内存）。
  这个区别很要紧——读成「量太小」会让人继续引用同一格里相邻的那几个数，
  而它们来自同一次被污染的成对计时。
- **优化 2 拿走了其余部分。**「两条独立路线」那张表是这件事的交叉核对，
  它的相差列就是这次归因的可信度：两条路线的输入、路径形状、测量时刻都不同，
  所以对得上才是真的对得上，而不是同一次测量换两种写法。
- **`sigmoid` 改写（优化 2a）的归因：本文早先的版本是错的，下面先给更正，
  再给更正后的数字。**

### 2.5 适用条件

- 优化 1 只在 **prompt 长于一个 chunk** 时触发：8 / 32 / 128 token 在默认
  `chunk_size=128` 下都只有 1 个 chunk，投影次数本来就是 1，**这一项完全不参与**。表里
  `base 投影` 列在这三行也是 1，不是 4。
- 优化 1 的绝对收益跟 `vocab_size × hidden_size` 走：一次投影从 0.86 ms 到 5.40
  ms（跨模型区间，取自上面那张表的「三者中位」列，作废行不计入）。
  小词表模型上它接近或低于这个探针自己的分辨率，分辨率见同表的「三次测量离散度」列。
- 优化 2a 的收益跟 `chunk_size × intermediate_size` 走（sigmoid 的输入形状），

## 3. 端到端工作负载

微基准说明算子层面省掉了什么，端到端说明用户感受到什么。5 个模型 × 5 个负载，每个 7
次取中位数（2 次预热后）。

**首 token 加速 1.18×–2.14×，整次请求墙钟加速 1.06×–1.62×**（数据源 `ab-longctx/`）。
墙钟的倍数明显低于首 token，因为**decode 那一段本轮没有被优化多少**（`raw_decode` 只有
1.05×–1.15×）：一个生成 64 token 的负载，decode 占掉大部分墙钟，prefill
省得再多也被摊薄。这正是 `multi-turn`（生成 11 token）和
`long-prompt-short-answer`（1662 进 / 32 出）的墙钟倍数最高的原因——它们的 prefill
占比最大。

### 3.1 这一节为什么跑了两遍，以及两遍不一致的地方

步骤 1 用 harness 默认的 `--max-context 1024`，而 `long-prompt-short-answer` 的 prompt
有 1662 token，**两棵树都因此拒绝执行**（不是 base 失败 opt
成功——分词发生在碰任何引擎之前）。被跳过的恰恰是唯一的 prefill 主导负载，也就是优化 1
针对的那个形状，缺了它这一轮最有力的证据就没测到，所以补跑了 `--max-context 2048`。

补跑还暴露了一件更要紧的事：
**同一份代码跑两遍，有四行结果相差超过 0.10×**。下面那张表把矛盾逐行公开，
而不是只留好看的那一遍。

数据来源：
`artifacts/perf-round1-rerun/ab-longctx/`，
`--max-context 2048`（`run_round1_longctx.sh`），五个负载全部测到。

每个工作负载 7 次取中位数（2 次预热后）。首 token = prefill + 第一个 token；
总耗时是整次请求的墙钟。
**输出 token 数不同的两行不能比**，所以表里带上生成数与停止原因，
`输出一致` 一列比较两侧的 `text_sha`。

**`decode 自检` = 该工作负载自己记录的 decode 速率 ÷ 同一棵树上裸 decode 探针的速率**（
`workloads[*].decode_seconds / generated_tokens` 除以
`micro.raw_decode.ms_per_token`）。它**不会等于 1.00**：长 prompt 负载的 KV
比探针长得多，逐 token 本来就更慢，所以 1.19、1.21 这种值是正常的。
要看的是**同一行 base 和 opt 的自检是否一致**——上下文长度在两侧相同、会互相抵消，
剩下的差异只能是那段时间机器的状态。

标记规则（写死在这里，不靠肉眼看表）：`base 自检` 与 `opt 自检` 相差超过 1.15×，
该行判为「待重测」。判据是两侧之比，所以与加速方向无关：一行声称变快 3×、但两侧自检差
2×，同样待重测。

这条规则原来是
`总加速 ≤ 1.00× 且 opt 自检 > base 自检 × 1.15`，
两个条件合起来意味着**只有声称变慢的行才可能被标记**——声称变快的那些行无论自检多离谱都原
样印成收益。那不是去噪，是只去掉碍事的噪声，剩下的行看起来比测量本身干净。

自检必须在**同一进程、同一时间窗**内采集才有意义：
它比较的是「这棵树在那几分钟里的机器状态」。借几小时前另一次运行的 micro 来配对，
得到的是**跨进程**比值，它混进了两次运行之间的机器漂移，
而这个漂移正是自检本来要抓的东西。所以没有同窗口 micro 的行自检列印 `—`，并按
**待重测（无同窗口自检）** 处理。

## 4. 优化 3：显式的多轮 KV 复用

### 4.1 省掉了什么工作

本轮之前，CLI 的 `chat` 每轮都新建引擎请求：
**第 n 轮要把前 n−1 轮的全部内容重新 prefill 一遍**。新增 `Engine.session()` →
`Session` 之后，同一个会话内已经算过并写进 KV 的前缀不再重算。

实测第 4 轮首 token 加速 2.75×–5.52×，整段四轮对话 1.10×–1.24×。第 1 轮必然是 1.00×
左右——没有东西可复用，如果第 1 轮也报出加速，那说明测的不是复用。

复用边界按**实际 token IDs 的最长公共前缀**决定，不按文本：BPE 会在轮次边界重新合并，
同一段文字重新分词后可能得到不同的 id 序列。
**少复用只是慢，多复用会让模型条件在一段它没见过的对话上。**表里的
`reused` 是引擎自己报告的复用 token 数，不是从 prompt 长度推的。

### 4.2 正确性怎么验的

- **cold 两遍的输出必须相同**，否则 reuse 改变了结果：5 个模型 × 7 轮 × 4 轮次 = 28
  次比较，**不一致 0 个**。
- 四个边界情况都有测试（`tests/test_session.py`，新增 52 项）：完全命中时仍要跑一个
  token（生成采样的是最后一个位置的 **logits**，不是 hidden state）；
  失败或取消的请求会让 cache 比 `_committed` 长，所以 `_plan` 先
  `del self._committed[length:]`；`_check_identity` 在模型或几何（层数、KV head 数、
  head dim、词表、`max_context`）变化时拒绝复用；图文会话直接拒绝。
- **普通独立请求仍然互相隔离**：`stream_ids` 的独立路径照旧 reset，
  两个平铺请求不可能看到彼此的 KV。§4 的不变量 2 因此有了一个**写明的**例外。
- `slowq chat` 默认走会话，`--no-reuse` 关掉，`/clear` 调 `session.reset()`，Ctrl-C
  取消生成后会话仍可用。

### 4.3 代价：第二份 cache

复用要能在历史被编辑时回退，所以会话持有第二份 cache。实测预留体积 24.0 MiB–224.0
MiB（随层数、KV head 数、`max_context` 走），开启时 CLI 会打印出来。
**这是本轮唯一一处明确的内存换时间**，只发生在会话路径上，独立请求路径不付。

**那个区间是在 `max_context=1024` 下测的**（`tools/benchmark.py` 的默认值，见 §1.2
的命令行）。预留是**按 `max_context` 一次分配**的，不随对话变长而增长，所以
[架构说明 §4](architecture.md#4-kv-cache-语义) 的每 token 表在 1024 下给出的正是这些值；
同一张表乘到 2048 就是 [架构说明 §6.1](architecture.md#61-多轮会话enginesession) 里
Qwen3-0.6B 的**约 448 MiB**。两个数都对，差别只在 `max_context`。

- 历史被编辑、`/clear`、模型或几何变化都会让复用失效并重新 prefill，这是正确性要求，
  不是性能缺陷。

## 5. 优化 4a：图像特征缓存

### 5.1 省掉了什么工作

对同一张图问第二个问题时，视觉塔（SmolVLM-256M 上占一次请求的绝大部分）
原来要**完整重跑一遍**。新增 `ImageFeatureCache` 之后，connector 之后的
`features` 被缓存，同图后续请求跳过整个视觉前向。

实测：同图同问第二次 7.08×，同图**换一个问题** 8.59×——features 与问题无关，
所以换问题照样命中。

### 5.2 正确性与失效

- 缓存身份包含**像素内容与形状、attention mask、crop 排布、原图 / resize 尺寸、
  encoder 尺寸、processor 配置、`Weights.fingerprint()`**。
  换一张图必须重算——实测那条路径只有 miss 没有 hit。
- `put` 拷入、`get` 拷出，两个请求不会持有同一个缓冲区，
  调用方改自己拿到的数组不会污染缓存。
- 带 `DebugProbe` 时**双向绕过**缓存：调试路径必须走真实计算。
- 生成结果：opt 侧 8 个生成步与关缓存基准比较，
  **不一致 0 个**，`all_steps_identical=True`；四条路径的实测缓存流量与从 step
  列表推出的期望逐条相符。
- 容量上限默认 128 MiB，`0` 关闭，负数报错。LRU 淘汰。
- **计时诚实**：
  `vision_encode_seconds` 在命中时记的是**本次请求自己的**像素哈希时间（实测 16.5 ms），
  不是当初那次前向的时长——把别人的耗时记在这次账上会正好掩盖缓存要证明的加速。
- CLI 的两个图文入口显式传 `image_cache_bytes=0`：一问一答即退出，
  缓存只会在没有任何后续请求会用到它的情况下白付一次像素哈希。库路径默认开启，
  那才是「对同一张图问第二个问题」真正发生的地方。

### 5.3 实测

`--warmup 1 --repeat 5 --max-new-tokens 32`，greedy。base
`cache_supported=False`（那棵树没有这个参数，所以它的四条路径都退化成「关缓存」），opt
`cache_supported=True`。

每条路径的 step 0 是冷的那次（必然 miss），step 1 是第二次请求。
第二次请求命中还是不命中，正是这张表要区分的。

#### 四条对照，各自回答一个不同的问题

| 对照 | 回答的问题 | before | after | 加速 | before 命中 | after 命中 |
| --- | --- | --- | --- | --- | --- | --- |
| base off-no-cache #1 → opt off-no-cache #1 | 优化 1+2 在图文路径上单独值多少（**缓存不参与**） | 2887.9 | 2715.3 | 1.06× | False | False |
| opt off-no-cache #1 → opt on-same-question #1 | **缓存本身**值多少，代码不变、同图同问 | 2715.3 | 383.4 | 7.08× | False | True |
| base off-no-cache #1 → opt on-same-question #1 | 升级并且问第二次，用户实际感受到的 | 2887.9 | 383.4 | 7.53× | False | True |
| opt off-no-cache #2 → opt on-second-question #1 | 同图**换一个问题**也命中——features 与问题无关 | 2633.6 | 306.7 | 8.59× | False | True |
| opt off-no-cache #1 → opt on-other-image #1 | 换一张图**必须**重算；这里 after 更慢是因为那张图更大（9 帧 vs 5 帧） | 2715.3 | 4792.2 | 0.57× | False | False |

`vision_encode_seconds` 在命中时是**本次请求自己**的像素哈希时间，
不是当初那次前向的时长。所以视觉编码那一行的倍数要读作「一次完整视觉前向 ÷

| 指标 | 关缓存 | 同问再问（命中） | 倍数 |

| 请求墙钟 | 2715.3 | 383.4 | 7.08× |

#### 正确性与缓存流量

- base：以 `off-no-cache` 为基准比较 3 个生成步，不一致 0 个，
  `all_steps_identical=True`。

- opt：以 `off-no-cache` 为基准比较 8 个生成步，不一致 0 个，
  `all_steps_identical=True`。

- opt
  四条路径的实测缓存流量与**从 step 列表推出来的期望**逐条相符（`matches_expectation`）；
  关缓存那条 `max_bytes=0`、hits/misses 全 0，换图那条只有 miss 没有 hit：

  - `off-no-cache`：hits=0 misses=0 entries=0 bytes=0 evictions=0 →
    `matches_expectation=True`

  - `on-same-question`：hits=7 misses=7 entries=1 bytes=737280 evictions=0 →
    `matches_expectation=True`

  - `on-second-question`：hits=7 misses=7 entries=1 bytes=737280 evictions=0 →
    `matches_expectation=True`

  - `on-other-image`：hits=0 misses=14 entries=2 bytes=2064384 evictions=0 →
    `matches_expectation=True`

峰值 RSS：关缓存 1.77 GiB，开缓存 2.20 GiB，差额 442.7 MiB —— 缓存条目本身只有 0.70
MiB，差额主要是命中路径少了一次前向、因而峰值出现的位置不同，
不能读成「缓存占了这么多内存」。

### 5.4 适用条件

- 收益只在**同一张图被问第二次及以后**出现。第一次永远 miss，并且要多付一次像素哈希（5
  帧 16.4 ms、9 帧 30.1 ms）。
- 换图必然重算，且换到更大的图会更慢（9 帧 vs 5 帧，实测 0.57×）——这一行不是回退，
  是那张图本身更大。倍数与 §5.3「四条对照」表里
  `opt off-no-cache #1 → opt on-other-image #1` 那一行同源。
- 文本 prefill 与 decode **不被这个缓存影响**（1.00× / 1.00×），所以请求墙钟的倍数（约
  7×）远小于视觉字段的倍数（约 141×）。

## 6. 优化 4b：预编码文档索引

### 6.1 省掉了什么工作

`EmbeddingEngine.search()` 每轮都把**全部文档重新编码一遍**：16 篇语料 × 8 条查询 =
每轮 128 次 document 编码。新增 `index_documents()` → `DocumentIndex` 之后，
`index.search(q)` 每轮只编码 query，document 编码次数为 **0**。

实测每轮墙钟：只查询 17.36×，即使**每轮都重建索引**也有 5.71×。
后一个数是刻意留的最保守读法——假设调用方一次都不复用索引。

**原有 `search()` 一字未改、仍可用。**进程内、不落盘、无 ANN、无 RAG。

### 6.2 正确性与失效

- 判据是**逐位相同**而不是
  `allclose`，编码次数由贴在实例上的探针数出来而不是从公式推——两者的细节与实测结果见
  §6.3。
- 失效条件：模型对象、tokenizer 对象、
  `prefill_chunk_size`、`Weights.fingerprint()` 中任一变化即拒绝复用。
  `prefill_chunk_size` 在表里是因为分块只保证 2e-4 等价、
  **不保证逐位相同**；`max_length` 与 `dimension` 不在表里，
  因为它们不改变已编码向量的值。

### 6.3 实测

语料 16 篇（合计 409 token），查询 ['慢炖是怎么加载权重的？', 'KV cache
为什么能加速解码？', 'How many times does the vision tower run per question?', '什么是
last-token pooling？', 'Why do two equal kernels produce different numbers?', 'What
makes a cache key safe?', '分块 prefill 的代价是什么？', 'How is cosine similarity
computed here?'] 条，
`--warmup 1 --repeat 3`，`max_length=8192`、`prefill_chunk_size=128`。base
`index_supported=False`（那棵树没有 `index_documents`），opt `index_supported=True`。

#### 每轮实际编码了多少次

计数来自一个**贴在实例上的探针**，包住 `encode_document` /
`encode_query`。`EmbeddingEngine.search`、`index_documents`、
`DocumentIndex.search` 三处都经实例属性调用，所以计到的是真实调用次数，不是从公式推的。

| 路径 | document 编码/轮 | query 编码/轮 | 每轮墙钟（中位数与全距） |
| --- | --- | --- | --- |
| base `engine.search` | **128** | 8 | 10014.1 ms [10009.4–10018.1] |
| opt `engine.search`（语义未改） | **128** | 8 | 7478.9 ms [7443.9–7738.8] |
| opt `index.search`（预编码） | **0** | 8 | 430.9 ms [429.2–433.5] |

#### 建索引的一次性成本

| 项目 | 值 |
| --- | --- |
| 建索引墙钟（16 篇编码一遍） | 878.6 |
| 其中 `index.build_seconds`（引擎自己记的） | 878.4 |
| 每次建索引的 document 编码次数 | 16 |
| 索引向量占用 | 0.06 MiB |
| `index.stats()` | `{"documents": 16, "tokens": 409, "dimension": 1024, "build_seconds": 0.8750207910015888, "searches": 0}` |
| 把重建摊进每轮之后的墙钟 | 1319.1 ms [1307.8–1382.5] |

#### 四种读法，不要混用

| 读法 | 回答的问题 | 数值 |
| --- | --- | --- |
| base search → opt search | 优化 1+2 在一个**语义未改**的 API 上白拿的部分 | 10014.1 → 7478.9 = **1.34×** |
| opt search → opt index | **索引本身**值多少，代码不变 | 7478.9 → 430.9 = **17.36×**（harness 记的 `queries_only` = 17.36×） |
| base search → opt index | 升级并改用索引，用户实际感受到的 | 10014.1 → 430.9 = **23.24×** |
| 每轮都重建索引 | **最保守**的读法：假设调用方一次都不复用索引 | 1309.5 ms/轮 = **5.71×** |

每 query 摊到的 document 编码次数：无索引 16.0，有索引 0.0。

#### 正确性

- 比较 40 条查询 × 4 个字段（ranking, similarity, query_vector, query_input_ids），
  判据是 `exact equality on the JSON round-tripped values`，不一致 0 个，
  `all_identical=True`。

- 判据是**逐位相同**而不是 `allclose`：两条路径调的是同一个 `rank_documents` /
  `encode_document`，所以本该一模一样；用容差比较会把一个真实的回归放过去。

- base 侧 `weights_fingerprint` = `null`（那棵树没有 `Weights.fingerprint`，记
  `null` 以保持两份输出同形状，而不是让 base 直接崩掉），opt 侧是 `6` 元组的前 6 项 +
  张量表。

- 峰值 RSS：base search 1.73 GiB，opt search 1.84 GiB，opt index 1.84 GiB。
  索引那条**不比 search 高**——省掉的是重复编码的中间激活，换来的只是那个向量矩阵。

### 6.4 适用条件

- **第 1 次查询就打平，不是「只查一次白花」。**建一次索引实测 **878.4 ms**（16
  篇文档各编码一次），而 `search()` 每查一次都要把这 16 篇重新编码一遍，每次省下
  **881.0 ms**。**这两件事是同一份工作**，所以查第 1
  次时建索引的成本刚好等于省下的成本，第 2 次开始净赚，之后每多查一次就多赚一次。
  （口径：建索引 878.4 ms ÷ 每次查询省下 881.0 ms = 1.00 次；语料 16 篇文档，每轮 8
  次查询。）
- 语料变了就要重建。索引不检测文档内容是否被原地改掉——身份表里记的是**建索引时**的
  fingerprint。

## 7. 优化 5：线程数与 prefill 分块参数——测了，默认值不动

### 7.1 结论先说

**两项默认值本轮都没有改动**，这是一个**有数据支撑的「不改」**，不是没做：

- **线程数**：四个配置（不设 / 1 / 4 / 8）之间，opt 侧 512-token 分块 prefill 的极差是
  1.8%（Qwen3-0.6B）、2.6%（SmolLM2-360M），decode 的极差是 4.1%（Qwen3-0.6B）、
  7.6%（SmolLM2-360M）。每个模型取两者中较大的那个，与本轮观测到的 约 3.0%
  跨进程离散度是 1.4 ~ 2.5 倍。**尚不能确认收益或回退。**请求的线程数**确实**在
  `import numpy` 之前进了环境（harness 记 `requested_before_numpy_import: true`），
  但耗时对它没有反应。至于是 Accelerate 忽略了这些变量、
  还是这些矩阵形状本来就受内存带宽限制，**本轮没有测，不做判断。**
- **`prefill_chunk_size`**：`c64`（+16.3% / +11.6%）和 `c512`（+1.5% / +6.2%）
  **明确更慢**；`c256`（-3.8% / +0.9%）
  按区间重叠判据属于**尚不能确认收益或回退**。
  没有任何一个非默认值落在「明确更快」那一档，所以 **128 不动**。

### 7.2 三个诚实声明

**「请求的线程数」不是「实际工作线程数」。**有效 BLAS 线程数在 Python 里不可观测，
harness 记为 `null` 而不是猜。所以下面任何结论都只针对「请求了这个数」。

**约 3.0% 不是一个「噪声底线」。**它是 §7.3 那张表里 `引擎分块 prefill 512 tok` 一行
opt 侧的**进程间**离散度（跨 6 轮独立进程取中位），它只说明一件事：
**不配对地**比较这个量，小于这个幅度分不出来。
**更正**：本文早先把一个同类的数称为「噪声底线」并写成「小于它的差不算收益」，
还写过「两个进程内区间互不重叠」。
两句都撤回——前者把**一个量的观测**当成了**所有负载的门限**，
后者在数据里只对一部分行成立（逐行判定见 §7.3）。
所以现在的判读规则**不引用任何统一百分比**：每个量用自己那几轮的**逐轮增益**判方向，
判不出来的一律写 `尚不能确认收益或回退`。

**方向性结论现在有了，

### 7.3 实测

每个配置一个**独立进程**。`t-default` 是完全不设线程环境变量，
也就是出厂默认——它必须被测量，不能假设等于任何一个显式数字。`requested` 是请求的线程数，
**有效工作线程数在 Python 里不可观测**，harness 记为 null，
所以下面任何结论都只针对「请求了这个数」而不是「跑起来用了这么多线程」。

**本轮没有 base 侧扫描数据**（`artifacts/perf-round1-rerun/baseline/` 下没有
`*-default-*.json`）。已发布那一轮的 `baseline/` 是**本轮之前**那棵树跑的，
重采时没有重建它——重建需要先检出一个更早的 revision，而重采的目标是用修复后的最终源码，
不是用旧树。所以下面两张表的 base 列全部是
`—`，**本节不支持任何 base→opt 比较**；能说的只有 opt 侧各配置之间的相对关系，
而且判读要用 §7 的跨进程离散度，不是同一进程内的 min–max 区间。

#### 跨进程离散度与逐轮配对增益（读下面两张表之前先看这个）

数据来自 `tools/perf/run_noise_floor.sh` 写入的
`noise-floor/`，**本表读的是 `artifacts/perf-round2-paired`**，不是
`--data` 那个根目录下的同名子目录。重测单独占一个目录，
是因为已发布的那一份是撤回结论背后的原始证据，重测只能**加**在它旁边，不能替换它；
两者都在磁盘上。
每对 base／opt 在独立进程里背靠背跑，多轮之间
**AB／BA 顺序交替**，
所以「谁排在第二个进程」不会与「谁是优化版」混在一起——第二个进程总是受益于已经热起来的
page cache，顺序不均衡的话那份好处会被记成优化的收益。

**每一行用这一行自己的多轮数据判读**，不引用任何统一的噪声百分比：`进程内` 是各进程自己
7 次重复的离散，`进程间` 是各轮中位数之间的离散，`逐轮增益` 是每一轮单独算一遍 base/opt
得到的那组数，`结论` 看这组数是否跨过 1.00。跨过了就是
`尚不能确认收益或回退`，与中位数落在哪一侧无关。

`弃用轮次` 是被污染判据剔掉的轮次，
判据有两条且**对 base／opt 同样严格**：**spike**（一个节点内 `max/median > 2.0`，抓「7
个样本里有 1 个停了几十秒」）与 **level**（该轮中位数 ÷ 各轮中位数的中位
`> 1.5`，抓「整轮一起变慢」——spike 抓不到它，因为 7 个样本一起抬高时
`max/median` 仍然接近 1）。两条都是量与自身尺度之比，所以不含毫秒门限，
换一台更快的机器也不会失效。
**判据按「量 × 轮 × 侧」逐格生效，不按整份文件生效**：一个进程在 512-token prefill
上停过，它的 decode 窗口仍然是可用的，按文件弃用会把那些一起丢掉。

`有效轮次` 与 `顺序均衡（保留轮次）` 两列都是**剔完之后重算的**，不是采集时的那个数。
这一步是必须的：AB／BA 均衡是「谁排在第二个进程」的均衡，而第二个进程继承热起来的 page
cache；剔掉一轮就可能把 2＋2 变成 2＋1，那时剩下的轮次里有一棵树系统性地占便宜，
**用它算出的方向不是测量的方向**。所以本表把 `轮数` 换成
`有效轮次`（真正算出配对增益的轮数），把 `顺序均衡` 明确标注为按保留轮次计算，
并且**只要这一列不是「是」，`结论` 就不给方向**——改判 顺序不均衡或未记录，
尚不能确认收益或回退；有效轮次少于 2 则改判 有效轮次不足，尚不能确认收益或回退。

进程内离散与进程间离散分开列，因为两者可以差一个量级，

也只说明那一个进程跟自己对得上。

**但判方向用的不是进程间那一列，是 `逐轮增益`。**这两件事不能混：
`进程间` 是**不配对**比较的分辨率——拿今天测的 base 去比昨天测的 opt，
差值小于它就分不出来。而这里每一轮的 base 与 opt

### 9.1 已完成、并且**观察到加速**

**下表里的倍数全部来自 `ab/`：每侧一个进程、

- **「稳定收益」本轮没有测到；测到的是「有限轮次方向一致」，
  由 §7.3 的配对实验判：**64/73 个（模型 × 量）
  达到**「有限轮次方向一致」**判据——每一轮独立进程各算一遍 base/opt、保留的有效配对 ≥

**测量纪律**（复现时若违反，数字不可比）：

- 严格串行，任何时刻只有一个基准在跑。
- A/B 的两棵树在**每个模型内部相邻交替**，不是先跑完一边。
- 固定模型 revision、输入 token IDs（`probe_token_ids` 确定性生成）、输出长度、
  线程（全部不设）、设备（CPU）、精度（FP32）、采样（greedy）。
- 预热 2 次后计时 7 次取中位数，并报告 min–max；
  首次前向与预热后稳态分开记（图像缓存那条路径的 step 0 必然 miss）。decode
  的重复单位是**窗口**（每次重新 prefill 同样的 id 到全新 cache，再跑固定步数），
  同一窗口内连续的 token 不算独立重复。
- 每份输出都记峰值 RSS、首 token、prefill、decode 与整次请求墙钟。
- 跨进程比较前先读 §7：那里是 AB/BA 配对的独立进程实验，进程内与进程间离散度分开记，
  每个量各自判定；判不出来的一律记 尚不能确认收益或回退，不要从单次运行里读方向。
