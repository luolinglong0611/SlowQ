### decode：逐 token 前向

`raw_decode` / `raw_decode_long` 是短 / 长上下文下的逐 token 前向，同样含优化 2 的两处改动（无分支 sigmoid + 单 token 时跳过全零 mask），这一轮没有把两者再拆开单独计时。

**decode 的重复单位是「窗口」，不是「token」。**一个窗口 = 用同一批 id 重新 prefill 一个新 cache，再跑固定步数的单 token 前向。每个窗口都从**相同的起始 token 序列、相同的 KV 长度、相同的上下文**开始，harness 还断言每个窗口结束时的 cache 长度完全一致（`cache_lengths_observed` 只有一个值）。计时边界只含那固定 步数的前向，**不含**建立起始状态的那次 prefill。一个窗口只产出一个样本（它的时长），所以「窗口数」就是样本数。

## 优化 1 与优化 2 的归因

`engine_prefill` 的加速是**优化 1 + 优化 2 之和**，两者极不均匀，所以必须拆开归因，不能把整个加速记在任何一项头上。

拆不开的原因要说清楚：`raw_prefill_full` 两棵树都只投影 1 次，它的差值确实只含优化 2，但它与引擎的分块循环**不是同一条路径形状**（一次全长 attention vs 四次逐渐变长的），所以它的绝对毫秒数不能直接从引擎的绝对毫秒数里减掉——只有比值能比。

`projection_probe.py` 直接补上缺的那一项：`forward` 就是 `encode` 加一次 `output_projection(hidden[-1])`（`model.py:390-398`），所以在同一棵树、同一批 id、同一个进程里**成对**计时再相减，得到的就是一次投影的净代价，权重、内存状态、进程全部固定。
`output_projection` 在两棵树之间**逐字节相同**（已 diff 核对），所以在 opt 树上测到的投影代价可以直接用来给 base 树当初多做的那几次定价。

**探针自身的精度**：一次投影的代价与块长无关（永远是 `[1, hidden] × [hidden, vocab]`），所以 128 / 256 / 512 三行是**同一个量的三次独立测量**，它们的离散度就是这个探针的误差棒。本批 105 对成对样本里有 **25 对为负**（23.8%，分布在 5/5 个模型上），最差的一对是 Qwen3-1.7B 在 128 token 上的 **-13419 ms**。而 `forward` 就是 `encode` 加一次真实存在的投影，**成对差值不可能为负**——出现负数只说明模型在成对计时的两半之间被换出了内存。所以**任何单次观测都不能用**，能用的是中位数；而中位数为负的那一行**整行作废**（下表标 `作废`，且不进「三者中位」）。


**其中 8 对负值落在中位数仍为正、因而没有被标 `作废` 的行里。**所以「没标作废」的准确含义是**这一格的 7 对里中位数为正**，不是「这一格测量干净」。这也是下面那个占比只能当区间读、且必须连着跨批次的重复性一起看的原因。

- 端到端上唯一测过这个量的实验是 §7.3 的配对实验，而它的 base／opt 两棵树**同时**差着优化 1 和优化 2，那几行的逐轮增益是两者之和。没有「只关优化 1」的配对探针，所以这个占比无论多大都分不出来。
- 这个占比自己的误差棒也不小：上面那张表的 `三次测量离散度` 列，是同一个 `[1, hidden] × [hidden, vocab]` 矩阵乘在 128／256／512 三个长度上的极差，相对幅度 4% ~ 166%——比被估的量本身还大。

**更正**：本节早先写的是「整个区间都不大于下面优化 5 那节观测到的跨进程离散度量级」，§9.2 那一行写的是「不大于约 1.5%」。两句都撤回。那个 1.5% 是**两个扫描模型**在 `引擎分块 prefill 512 tok` 一行 opt 侧进程间离散度的中位数，拿它去比**四个模型里最大的占比**，是跨模型比两列不同的东西；而按模型各比一遍时，占比最大的 Qwen3-0.6B 自己那一行的 opt 侧进程间离散度**比它的占比还小**（数字在 §7.3 表里，不在此处复述），所以「不大于」按模型读也不成立。撤回这个比较不改变结论——结论靠的是上面第一条「拆不出来」，它不引用任何离散度。
它保留在代码里的理由是免费且逐位相同，不是因为它快。

### 两条独立路线给优化 2 定价，互相核对

路线 A：`引擎实测省下 − 探针测到的 3 次投影` = 优化 2。
路线 B：`raw_prefill_full` 的 base−opt 差值 = 优化 2（两棵树都只投影 1 次）。
两条路线用的输入不同、路径形状不同、连测量时刻都不同，所以它们对得上才是真的对得上。`相差` 一列大到与下面优化 5 那节的跨进程离散度同量级，就说明三项测量里有一项是错的。

**整行跳过的两种情况**（跳过而不是印一个数出来）：
- 探针 512 tok 的成对差值中位数 ≤ 0 —— 路线 A 会**减去一个负数**，把优化 1 的功劳算到优化 2 头上，越脏的探针算出来优化 2 越大。
- `raw_prefill_full` 的自检不过（上面那张表的 `自检` 列 >1.15×）—— 路线 B 整个是机器状态，不是代码。

## 端到端工作负载

数据来源：`artifacts/perf-round1-rerun/ab-longctx/`，`--max-context 2048`（`run_round1_longctx.sh`），五个负载全部测到。

每个工作负载 7 次取中位数（2 次预热后）。首 token = prefill + 第一个 token；总耗时是整次请求的墙钟。**输出 token 数不同的两行不能比**，所以表里带上生成数与停止原因，`输出一致` 一列比较两侧的 `text_sha`。

**`decode 自检` = 该工作负载自己记录的 decode 速率 ÷ 同一棵树上裸 decode 探针的速率**（`workloads[*].decode_seconds / generated_tokens` 除以 `micro.raw_decode.ms_per_token`）。它**不会等于 1.00**：长 prompt 负载的 KV 比探针长得多，逐 token 本来就更慢，所以 1.19、1.21 这种值是正常的。要看的是**同一行 base 和 opt 的自检是否一致**——上下文长度在两侧相同、会互相抵消，剩下的差异只能是那段时间机器的状态。

标记规则（写死在这里，不靠肉眼看表）：`base 自检` 与 `opt 自检` 相差超过 1.15×，该行判为「待重测」。判据是两侧之比，所以与加速方向无关：一行声称变快 3×、但两侧自检差 2×，同样待重测。

这条规则原来是 `总加速 ≤ 1.00× 且 opt 自检 > base 自检 × 1.15`，两个条件合起来意味着**只有声称变慢的行才可能被标记**——声称变快的那些行无论自检多离谱都原样印成收益。那不是去噪，是只去掉碍事的噪声，剩下的行看起来比测量本身干净。

自检必须在**同一进程、同一时间窗**内采集才有意义：它比较的是「这棵树在那几分钟里的机器状态」。借几小时前另一次运行的 micro 来配对，得到的是**跨进程**比值，它混进了两次运行之间的机器漂移，而这个漂移正是自检本来要抓的东西。所以没有同窗口 micro 的行自检列印 `—`，并按 **待重测（无同窗口自检）** 处理。

## 优化 5：线程数与 prefill 分块参数

每个配置一个**独立进程**。`t-default` 是完全不设线程环境变量，也就是出厂默认——它必须被测量，不能假设等于任何一个显式数字。`requested` 是请求的线程数，**有效工作线程数在 Python 里不可观测**，harness 记为 null，所以下面任何结论都只针对「请求了这个数」而不是「跑起来用了这么多线程」。

**本轮没有 base 侧扫描数据**（`artifacts/perf-round1-rerun/baseline/` 下没有 `*-default-*.json`）。已发布那一轮的 `baseline/` 是**本轮之前**那棵树跑的，重采时没有重建它——重建需要先检出一个更早的 revision，而重采的目标是用修复后的最终源码，不是用旧树。所以下面两张表的 base 列全部是 `—`，**本节不支持任何 base→opt 比较**；能说的只有 opt 侧各配置之间的相对关系，而且判读要用 §7 的跨进程离散度，不是同一进程内的 min–max 区间。


### 跨进程离散度与逐轮配对增益（读下面两张表之前先看这个）

数据来自 `tools/perf/run_noise_floor.sh` 写入的 `noise-floor/`，**本表读的是 `artifacts/perf-round2-paired`**，不是 `--data` 那个根目录下的同名子目录。重测单独占一个目录，是因为已发布的那一份是撤回结论背后的原始证据，重测只能**加**在它旁边，不能替换它；两者都在磁盘上。
每对 base／opt 在独立进程里背靠背跑，多轮之间 **AB／BA 顺序交替**，所以「谁排在第二个进程」不会与「谁是优化版」混在一起——第二个进程总是受益于已经热起来的 page cache，顺序不均衡的话那份好处会被记成优化的收益。

**每一行用这一行自己的多轮数据判读**，不引用任何统一的噪声百分比：`进程内` 是各进程自己 7 次重复的离散，`进程间` 是各轮中位数之间的离散，`逐轮增益` 是每一轮单独算一遍 base/opt 得到的那组数，`结论` 看这组数是否跨过 1.00。跨过了就是 `尚不能确认收益或回退`，与中位数落在哪一侧无关。

`弃用轮次` 是被污染判据剔掉的轮次，判据有两条且**对 base／opt 同样严格**：**spike**（一个节点内 `max/median > 2.0`，抓「7 个样本里有 1 个停了几十秒」）与 **level**（该轮中位数 ÷ 各轮中位数的中位 `> 1.5`，抓「整轮一起变慢」——spike 抓不到它，因为 7 个样本一起抬高时 `max/median` 仍然接近 1）。两条都是量与自身尺度之比，所以不含毫秒门限，换一台更快的机器也不会失效。**判据按「量 × 轮 × 侧」逐格生效，不按整份文件生效**：一个进程在 512-token prefill 上停过，它的 decode 窗口仍然是可用的，按文件弃用会把那些一起丢掉。

`有效轮次` 与 `顺序均衡（保留轮次）` 两列都是**剔完之后重算的**，不是采集时的那个数。这一步是必须的：AB／BA 均衡是「谁排在第二个进程」的均衡，而第二个进程继承热起来的 page cache；剔掉一轮就可能把 2＋2 变成 2＋1，那时剩下的轮次里有一棵树系统性地占便宜，**用它算出的方向不是测量的方向**。所以本表把 `轮数` 换成 `有效轮次`（真正算出配对增益的轮数），把 `顺序均衡` 明确标注为按保留轮次计算，并且**只要这一列不是「是」，`结论` 就不给方向**——改判 顺序不均衡或未记录，尚不能确认收益或回退；有效轮次少于 2 则改判 有效轮次不足，尚不能确认收益或回退。

**真实样本量与不确定性：**每行只有 4–6 轮独立进程，不是几十次重复。四条判据给的是**方向**，不是**大小**，也不是「统计上不可能反号」：4 轮全部同向在抛硬币下本就有可能（p = 0.0625），所以本节把幅度交给 `进程间` 那一列，而它比这里的极差大。要说「稳定收益」，需要的是预先声明的轮数下限、幅度超过进程间离散度、以及跨机器复现，本轮三者都没有。


把全部 73 行的逐轮增益汇到一起做符号检验：**429 个配对里 420 个大于 1.00**，双侧精确二项 p = 1.84e-111。**这个 p 值只回答「一枚硬币抛这么多次会不会这么偏」，不回答「每一行都变快了吗」**：同一个进程贡献了好几个量、同一台机器贡献了 5 个模型，这些行不独立，汇总的 p 值因此**高估**证据强度。要按行看，看上面那张表的 `结论` 列。**这个 p 值也把上面那些不均衡、轮次不足的轮次一起算了进去**，所以它比逐行判据更宽松，不能拿来替代那一列。


进程内离散与进程间离散分开列，因为两者可以差一个量级，而**能用来判断「这个差是不是真的」的只有进程间那一列**：进程内区间再紧，也只说明那一个进程跟自己对得上。

**但判方向用的不是进程间那一列，是 `逐轮增益`。**这两件事不能混：`进程间` 是**不配对**比较的分辨率——拿今天测的 base 去比昨天测的 opt，差值小于它就分不出来。而这里每一轮的 base 与 opt 是**背靠背两个独立进程、同一台机器、同一份权重**，机器状态的那部分噪声在相除时抵消掉了。

**但抵消的前提是顺序均衡，而均衡只对保留下来的轮次成立。**排在第二个进程的那棵树继承热起来的 page cache，所以 `顺序均衡（保留轮次）` 为「否」的行里，那份便宜会被记成优化的收益——这类行本表一律判 `顺序不均衡或未记录，尚不能确认收益或回退`，不给方向。均衡为「是」的行才谈得上「`有效轮次` 那一列的轮数全部落在 1.00 同一侧是有信息的」，即使那几个比值本身的极差小于 `进程间` 那一列。反过来说：这个判据给的是**方向**，不是**大小**。一行的 `逐轮增益` 挤在 1.00 上方一点点（本表 Qwen3-0.6B 的两行 decode 就是），意思是「这几次配对都偏快」，**不是**「已经确定快了那么多」——要定价还得看 `进程间`。

**这张表不提供任何可以套到别的量上的统一门限。**下面两张扫描表比的都是 `引擎分块 prefill 512 tok`，所以它们引用的离散度取自上表这一行的 opt 侧进程间值（两个扫描模型的中位 3.0%），是同一个量的同类测量，不是从别的量借来的常数。扫描表只覆盖这两个模型，所以这个中位数也只在这两个模型里取——把另外三个模型的离散度混进来，等于又造了一个统一门限。
