# SlowQ 推理加速调研

调研日期：2026-10-23。代码基线：`8968e39`，SlowQ v0.2。

本轮结合本地源码、已有性能记录，以及公开论文、官方文档和作者维护的实现进行筛选。检索覆盖 CPU/NumPy 算子、缓存复用、推测解码、量化、注意力、视觉与向量任务及可选后端；不声称穷尽全部互联网内容。本文是研究与实验建议，没有实施加速、重新跑性能基准或测得新的加速倍数。

**结论：先消除确定的重复计算，再优化数据搬运和算子；如果需要明显提高持续生成速度，再验证量化内核与推测解码。** 保留纯 NumPy FP32 路径作为可读、可验证的参考实现，可选加速后端独立演进。

## 现状与瓶颈判断

项目目前是 CPU、FP32、batch size 1，运行时依赖为 NumPy、tokenizers、Jinja2。已有只读 mmap、预分配 KV cache、分块 prefill、不物化重复 K/V 的 GQA，以及每次 forward 只投影最后一个位置。这些已经存在的能力不能再列作新增优化。

## 优先级总表

优先级按当前实现的适配度、确定能省掉的工作及改动成本排序，不代表已测速度排名。

| 优先级 | 方法 | 主要改善什么 | 改动量 / 前提 |
| --- | --- | --- | --- |
| P0 | 非末 prefill chunk 跳过 lm_head | 长 prompt 首 token 延迟 | 小；现有 encode 接口即可利用 |
| P0 | 多轮对话复用相同 token 前缀的 KV | 多轮或固定前缀 prefill | 中；需会话状态和正确失效/回滚 |
| P0 | 缓存图片 connector features | 同图重复问答 | 小到中；首次看图无收益 |
| P0 | 预编码并复用文档向量 | 固定文档集合的重复查询 | 小；无需引入向量数据库 |
| P1 | decode 跳过全零 mask、减少临时数组 | 算子开销与内存流量 | 小到中；保留 debug probe 语义 |
| P1 | BLAS 线程与 prefill chunk 参数扫描 | 不同模型/输入的实际速度 | 小；当前已使用 Accelerate |
| P1 | QKV / gate-up 投影打包、预绑定权重 | 调用次数、矩阵乘法效率 | 中；不可在每次 forward 拼权重 |
| P1 | 视觉 attention 按 query 分块 | 视觉首 token 延迟和峰值内存 | 中；所有 query 仍看完整 K/V |
| P2 | 视觉帧微批、embedding 长度分桶 batch | 批量吞吐、权重复用 | 中到大；扩展当前 batch 1 范围 |
| P2 | prompt lookup / 小模型推测解码 | 输出多个 token 所需的目标模型调用 | 大；验证、回滚、接受率决定收益 |
| P2 | Q8/Q4 权重 + 原生量化矩阵乘内核 | decode 吞吐、内存、冷启动 | 大；有数值变化，新增后端/格式 |
| P2 | MLX / GGML / 图编译可选后端 | 平台内核或 GPU 加速 | 大；保留 NumPy 参考路径 |
| P3 | KV 量化、分页、稀疏注意力 | 长上下文或高并发 | 当前基准 1024 / 单请求下优先级较低 |

## 可先在现有 NumPy 路径落地的工作

### 1. 非末 prefill chunk 不计算词表输出

这是直接由源码确认的冗余工作。[engine.py:348](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/engine.py:348>) 对每个 chunk 调用 `model.forward()`，后面只保留最后一个 chunk 的 logits；而 [model.py:356](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/model.py:356>) 每次都会执行完整词表投影。

建议中间 chunk 调用 `model.encode()`，最后一块调用 `forward()`。`encode()` 已完成所有层的 K/V 写入及 cache commit。启用需要 logits 的 debug probe 时，保留原路径或显式提供同等观测能力；同时让 benchmark 的分块路径与引擎实现保持一致。

Qwen3-0.6B 的词表投影矩阵为 `151936×1024×4` 字节，即 **593.5 MiB**；1.7B 的矩阵为 **1187 MiB**。512 token、chunk=128 时可以少做 3 次词表矩阵乘法，相应矩阵逻辑体积为 1780.5 / 3561 MiB。这里是省掉的运算和逻辑访问量，不是实际 DRAM 流量或实测提速。短于一个 chunk 的输入和稳态 decode 没有这项收益。

### 2. 多轮会话保留 KV，只 prefill 新增后缀

[engine.py:329](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/engine.py:329>) 在每次请求开始清空 cache 的有效长度。因此目前即使 CLI 保留了聊天历史，模型也会重新计算历史。

可引入显式会话对象，保存已计算的 token IDs、KV 的有效长度和必要的最后 logits；下一次 chat template 渲染后，求**实际 token 序列的最长公共前缀**，只计算其后的内容。前缀缓存减少重复 prefill，不直接减少新 token 的逐步 decode 成本。[vLLM 官方说明](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)

实现条件：

- 缓存的是 token 前缀，不能按字符串长度推断。CLI 会把输出文本重新放入模板，重新分词后未必等于上次生成的原始 token IDs。
- 当前循环先采样、再在下一步把 token 写入 KV，停止时最后一个生成 token 尚未进入 KV；需要明确这一个 token 的归属。
- 对历史编辑、取消生成、system prompt 变化、模型或 tokenizer revision 变化做失效处理。完全命中时还需复用对应 logits，或重算最后一个 token。
- 提供安全的 `truncate/rollback`，只允许读取已经提交的有效前缀；多模态前缀还必须包含图片特征身份，单凭 `<image>` token IDs 不足以识别图片。

### 3. 缓存图片特征与文档向量

**图片：** [vlm.py:1319](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/vlm.py:1319>) 每次生成前重新 `encode_image()`。connector 输出不依赖问题文本，可按图片内容、预处理配置、模型 revision 和精度缓存最终 features。MLX-VLM 已有同类的 [Vision Feature Caching 实现说明](https://github.com/Blaizzy/mlx-vlm#vision-feature-caching)。

当前样例 320 / 576 个 image token、hidden=576，最终 FP32 features 仅约 **0.70 / 1.27 MiB**；无需保留整个视觉塔的中间张量。命中后跳过视觉编码，首次看图不受益。采用有容量上限的缓存，并使命中时的计时反映实际发生的工作。debug 模式若需要中间视觉结果，应重算或单独保留观测数据。

**文档：** [embedding.py:379](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/embedding.py:379>) 的 `search()` 每次都重新编码全部 documents。增加“先编码文档、后查询”的接口，或按内容和模型配置缓存向量，即可让后续请求只算 query 与点积。1024 维 FP32 向量每条只占 4 KiB。模型、tokenizer、文本及编码配置必须进入缓存身份。

### 4. 减少无用 mask、数组分配和 Python 调度

[model.py:298](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/model.py:298>) 无条件创建 causal mask。在当前完整因果注意力、只读有效 cache 的单 token decode 中，所有 key 都可见，mask 全零；可直接传 `None`，省去每层加 mask 产生的数组。多 token prefill 仍需正确的带 offset 因果 mask。

[ops.py:138](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/ops.py:138>) 的 softmax 和 [ops.py:208](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/ops.py:208>) 的 attention 会产生多个与 scores 同尺寸的临时数组。可使用受控的 `out=` 工作缓冲，复用 softmax、RoPE、归一化与激活的部分临时存储。模型调用方目前丢弃 attention 返回的 scores，可增加 `return_scores=False` 内部快路；算子默认返回 pre-softmax scores 的契约仍需保留，不能覆盖后返回伪装的 scores。当前 DebugProbe 并不提供 attention scores 观测。[NumPy ufunc 的 out 参数](https://numpy.org/doc/stable/reference/ufuncs.html)

[weights.py:258](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/weights.py:258>) 会在投影调用时重复查询、构造 shape 并校验。加载期建立每层结构并预绑定已验证的数组，可以减少热路径 Python 工作；不能删除加载期的完整性检查。RoPE 表也可以缓存，但当前已经每次 forward 只算一次、由所有层共享，不能按“每层都重算”估计收益。

上述方案都需要 profile 定位，尤其大模型 decode 的瓶颈若主要是读取权重，减少 Python 调用只会带来有限收益。

### 5. 合并投影与参数扫描

[model.py:500](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/model.py:500>) 分别进行 Q/K/V 投影；[model.py:563](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/model.py:563>) 分别进行 gate/up 投影。可在转换期或加载期打包为 QKV 和 gate-up 矩阵，一次 matmul 后切分输出，减少每层调用次数。Q/K norm 与 RoPE 仍在正确的切分位置执行，且保留家族间的 bias 差异。

这种融合没有减少模型权重总量。每 token 用 `concatenate` 拼接权重会引入大拷贝；加载期同时保存原版和打包版也可能明显增加 RSS。因此优先考虑可选的转换期布局，并分别测 GEMV decode 与 GEMM prefill。更大的 GEMM 形状不等于一定更快。

现有 benchmark 已能设置线程数，但默认值不代表最优值。建议独立进程扫描 `default/1/2/4/8` 线程与 `32/64/128/256/512` chunk，对短文本、长 prompt、视觉编码分别比较。先修复多余 lm_head，再判断 chunk 大小的收益，避免参数优化掩盖冗余工作。[NumPy 线程与 BLAS 说明](https://numpy.org/doc/stable/reference/global_state.html)

本项目已使用 Accelerate；不能把“切换到 Accelerate”当作尚未实施的提升。NumPy 官方的 [Accelerate 支持说明](https://numpy.org/doc/2.0/release/2.0.0-notes.html#macos-accelerate-support-including-the-ilp64)可用于确认环境，文中的通用线代提速并非本项目可再获得的倍数。

### 6. 视觉 attention 分块，再尝试帧微批

视觉每帧有 1024 个 patch。12 个 head 的一份 FP32 attention scores 约为 `12×1024×1024×4=48 MiB`；概率和 softmax 临时数组会继续增加峰值。[vlm.py:1060](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/vlm.py:1060>) 使用的通用 attention 会完整物化这些矩阵。

低复杂度方案是**按 query 分块**，让每块 query 仍访问该帧全部 K/V，输出按原顺序拼回。这样不裁 patch、不改变可见性，可以降低峰值内存；Python 循环和小 GEMM 可能抵消速度收益，必须测量。

进一步按 key 分块时，需要 online softmax 正确合并分块最大值、指数和及加权输出，不能每块各做 softmax 后直接拼接。[FlashAttention 论文](https://arxiv.org/abs/2205.14135)提供了减少 attention 中间存储的算法依据，但其 GPU kernel 与论文倍数不能直接移植成 NumPy CPU 的性能保证。

[vlm.py:943](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/vlm.py:943>) 当前逐帧跑完整个视觉塔，可试每层处理 2/4 帧的微批，复用权重并做更大矩阵乘法。各帧 attention 必须独立，不能把 patch 拼成可跨帧注意的单序列；内存随微批增大，建议在降低 scores 峰值后验证。

embedding 的 [encode_many](</Users/lilele/Desktop/慢炖 · SlowQ/src/slowq/embedding.py:341>) 也是顺序执行。长度分桶 batch 可作为后续吞吐优化，但要增加 padding mask、position IDs 和 last-valid-token pooling；不能简单串接文档。参考 [Qwen3-Embedding 官方批量编码示例](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B#transformers-usage)。单次完整 prefill 的短文本还可直接使用当前层计算的 K/V，省去写入持久 KV cache 的复制；分块长文本仍需缓存历史 token。该专用路径主要减少分配与复制，收益需要单独验证。

## 需要独立实验的算法和后端

### 7. 推测解码：先 prompt lookup，再小模型 draft

思路是便宜地提出多个候选 token，由目标模型一次前向验证；只有接受足够多的候选时，额外 draft 和验证开销才划算。标准 speculative sampling 可以保持目标分布，但必须实现接受/拒绝和拒绝后的修正采样，不能把“候选看起来差不多”当接受条件。保持目标分布也不等于固定 seed 后与原逐 token 实现生成完全相同的文本。[原始论文](https://arxiv.org/abs/2211.17192)

对 SlowQ 推荐两个实验：

1. **Prompt lookup / n-gram draft。** 从已有 prompt 中提出候选，不加载第二个模型；更适合摘要、改写、代码补全等存在原文复用的任务。开放聊天可能接受率低，需自动缩短或关闭。参考 [Transformers prompt lookup 文档](https://huggingface.co/docs/transformers/main/assisted_decoding#prompt-lookup-decoding)。
2. **Qwen3-0.6B draft → Qwen3-1.7B target。** 本轮已核对本地两个转换目录的 `tokenizer.json` 和 `tokenizer_config.json`，两份文件分别逐字节相同；SmolLM2-135M / 360M 也是可配对的同 tokenizer 候选。更换 revision 后仍需重新核对 token-ID 映射、特殊 token 与模板。历史基准中，Qwen 草稿单步耗时约为目标的 40%，Smol 草稿约为目标的 50%，额外权重读取成本不可忽略。CPU 上可能得不偿失，不能预设一定提速。

本地 Qwen tokenizer 文件 SHA-256 校验记录：`tokenizer.json` 为 `aeb13307a71acd8fe81861d94ad54ab689df773318809eed3cbe794b4492dae4`，`tokenizer_config.json` 为 `d5d09f07b48c3086c508b30d1c9114bd1189145b74e982a265350c923acd8101`。目录为 [Qwen3-0.6B-slowq](</Users/lilele/Desktop/慢炖 · SlowQ/models/Qwen3-0.6B-slowq>) 与 [Qwen3-1.7B-slowq](</Users/lilele/Desktop/慢炖 · SlowQ/models/Qwen3-1.7B-slowq>)。

现有代码还缺：候选各位置 logits 的批量投影、目标与 draft 双 cache、拒绝后的回滚、EOS/长度边界处理，以及接受率/每轮接受 token 数的指标。`model.forward()` 只返回最后位置 logits，不能直接用于多位置验证。可先实现 greedy 验证以缩小正确性范围，再实现保持采样分布的版本。

近期训练式 draft 也值得保留为研究项：

- [EAGLE-3 官方仓库](https://github.com/SafeAILab/EAGLE)列出第三方 [AngelSlim/Qwen3-1.7B_eagle3](https://huggingface.co/AngelSlim/Qwen3-1.7B_eagle3)，因此并非我们所有尺寸都没有现成 draft；但仍需新权重、特征导出、draft 架构与验证/回滚支持。
- 2026 年的 [DFlash 论文](https://arxiv.org/abs/2602.06036)和[作者实现](https://github.com/z-lab/dflash)属于另一条训练式 block draft 路线；本轮看到的公开 Qwen3 列表未覆盖我们的 0.6B/1.7B，不能直接作为当前配置开关使用。

### 8. 权重量化必须与能消费压缩权重的内核一起做

在带宽压力较大的 decode 场景，减少每次读取的权重字节数具有较高潜力。[AWQ](https://arxiv.org/abs/2306.00978)和[GPTQ](https://arxiv.org/abs/2210.17323)是可借鉴的低比特权重量化方法；具体 checkpoint 的误差必须重新评估。

FP32→INT8/INT4 的原始权重存储理论上降至 FP32 的 1/4 或 1/8，尚未计入 scale、zero point 和未量化张量，**不能据此声称 4/8 倍加速**。如果每层每 token 都完整反量化回 FP32 再调用 NumPy matmul，转换和临时数组可能抵消收益。[ONNX Runtime 官方量化性能说明](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html#why-am-i-not-seeing-performance-improvements)

可先用成熟 CPU 后端的 Q8/Q4 建立对照，再决定是否实现 SlowQ 教学版的分组量化和融合 dot kernel。量化模式应有独立的模型格式、加载检查、误差报告和质量评估，不能悄悄放宽现有 FP32 正确性门限。

适合进一步读的 CPU 路线：

- [Microsoft T-MAC](https://github.com/microsoft/T-MAC)：通过查找表支持低比特混合精度矩阵乘，避免传统完整反量化；有 Apple Silicon 等 CPU 路径。其历史性能比较有特定 llama.cpp 基线版本和模型条件，且构建涉及 TVM/LLVM，不是轻依赖替换。
- [Vec-LUT / vlut.cpp，MobiSys 2026](https://github.com/OpenBitSys/vlut.cpp)：面向并行低比特计算，覆盖 prefill、服务和推测验证等场景，值得作为后续量化 GEMM 研究；本轮未验证它对我们八个 checkpoint 的端到端支持。
- [llama.cpp 的 Arm KleidiAI 支持](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md#arm-kleidiai)：提供硬件特定微内核，但是否采用取决于 CPU 特性、张量格式、shape 与运行时选择；编译开启不代表所有算子已加速。

### 9. 可选后端：优先做有边界的原型

| 后端路线 | 对 SlowQ 的实际价值 | 边界与验证要求 |
| --- | --- | --- |
| MLX | Apple Silicon 上试快速 attention、量化 matmul，或先替换昂贵的视觉塔 | 新增 MLX/平台依赖；GPU 使用要明确标注，固定精度和输入对照 |
| llama.cpp / GGML | 量化 CPU 内核、Metal，以及成熟实现的端到端参照 | 需要 GGUF 与对应模型支持；属于另一执行后端，不能算作纯 NumPy 改动 |
| ONNX Runtime | 先试固定每帧尺寸的视觉塔与图融合 | 导出、fusion 是否命中及算子覆盖需检查；动态 decode 的 cache 接口更复杂 |
| 可选 Numba / 原生扩展 | 融合 RMSNorm、RoPE、SiLU、softmax 等经 profile 证实的热点 | 不能假定重写 matmul 能胜过现有 BLAS；计入编译和维护成本 |

MLX 官方提供 [scaled_dot_product_attention](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.fast.scaled_dot_product_attention.html) 和 [quantized_matmul](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.quantized_matmul.html)。MLX-VLM 还有实际的 [Idefics3 视觉实现](https://github.com/Blaizzy/mlx-vlm/blob/main/mlx_vlm/models/idefics3/vision.py)，适合做数值与性能参照。

llama.cpp 的 [构建文档](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)明确区分 CPU、BLAS、Metal 等后端；在 Apple 机器做 CPU 对照时，应禁用 Metal 等其他执行设备并检查运行日志，不能只看到 CPU 存在就认为是纯 CPU 测试。ONNX Runtime 的 [图优化文档](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html)列出了 MatMul+Add、GELU、LayerNorm 和 attention 等融合。

编译逐元素核可参考 [Numba 性能指南](https://numba.readthedocs.io/en/stable/user/performance-tips.html)与[兼容性表](https://numba.readthedocs.io/en/stable/user/installing.html#version-support-information)，首轮编译时间单列，先保持严格浮点行为。Apple CPU 还可研究 [BNNS Graph](https://developer.apple.com/videos/play/wwdc2024/10211/) 的整图优化，但桥接、算子覆盖和转换成本使它更适合长期后端实验。

## 有价值但目前应后置的方向

- **KV cache 量化：** [KIVI](https://arxiv.org/abs/2402.02750)、[TurboQuant](https://arxiv.org/abs/2504.19874)值得用于长上下文实验。两个 Qwen3 的 FP32 KV 都是 224 KiB/token：1024 token 为 224 MiB，8192 token 为 1.75 GiB，后者才明显提高优先级。量化/反量化和旋转开销要纳入 CPU 计时。Google 在 2026 年的 [TurboQuant 说明](https://research.google/blog/turboquant-redefining-ai-efficiency-with-extreme-compression/)中报告的最高 8 倍是 H100 上特定 attention logits 计算，不是 SlowQ 端到端加速；任务分数保持不变也不等于逐元素完全无误差。
- **PagedAttention、continuous batching：** [PagedAttention 论文](https://arxiv.org/abs/2309.06180)主要解决服务场景下的 KV 管理与并发利用。当前单请求、连续预分配 cache 已避免逐 token 拼接，先增加分页调度很可能只增加复杂度。服务化之后再评估吞吐与 P95 延迟。
- **Sparse attention、token pruning、减少 crop：** 会改变关注的信息或模型计算。它们可以作为质量/速度可调模式，但不能归入保持当前参考语义的优化。
- **直接把 dtype 改为 FP16：** 内存更小不保证 NumPy CPU matmul 更快，且当前加载器、算子和验证都以 FP32 为前提。应在具有相应优化 kernel 的后端内作为独立精度配置验证。
- **训练成低比特模型、蒸馏或改模型结构：** 可能改变性能上限，但需要新的权重和质量评估，超出“加速当前八个 checkpoint”的直接改造范围。
- **只优化 top-p：** 当前基准全部为 greedy，已有 argmax 快路，优化 top-p 不会改善这些基准。若实际工作负载以随机采样为主，可在已有 `np.partition` top-k 后，只对候选集合执行后续排序/概率计算；必须保持 ties、过滤顺序及随机数语义。

## 建议的验证顺序与验收

**第一轮：保持纯 NumPy FP32。** 增加按阶段的 profile，单独验证非末 chunk 跳过 lm_head、decode 零 mask 快路、视觉 query 分块与参数扫描；按真实使用场景增加多轮 KV、视觉特征、文档向量缓存。每个改动独立 A/B，最后组合回归，避免把收益混在一起。

**第二轮：针对持续 decode。** 在 Qwen3-1.7B 上分别做 prompt lookup、0.6B draft，以及 Q8/Q4 原生后端对照。记录接受率、验证时间、draft 时间与端到端 tokens/s；只保留收益超过噪声且符合质量要求的路径。

**第三轮：针对目标平台。** Apple Silicon 先试 MLX 视觉塔或完整可选后端；CPU 通用路线优先验证成熟量化内核，再决定自研程度。若加入 batch 或长上下文，再推进缓存量化、批调度和分页。

| 验证维度 | 应记录或覆盖的情况 |
| --- | --- |
| 正确性 | 沿用现有 FP32 参考门限；检查 hidden/logits、greedy token、chunk/cache 一致性与 debug probe |
| 缓存正确性 | 命中/未命中、前缀变化、完全命中、取消、EOS、最后 token 未提交、换图、换模型 |
| 量化质量 | 独立报告 logits/向量误差、语言质量或 perplexity、检索排序、视觉任务质量，不修改 FP32 门限来制造 PASS |
| 主要工作负载 | 短/长 prompt；短/长输出；多轮；同图重复问答；固定文档重复搜索；greedy 与实际随机采样 |
| 速度 | 首 token、prefill、decode、视觉编码、query/document 编码与完整请求墙钟时间 |
| 内存 | 权重逻辑体积、KV 容量、缓存占用、峰值 RSS 分开报告 |
| 测量方法 | 固定 checkpoint/revision、token IDs、输出长度、线程、BLAS、设备与精度；区分首次前向和稳态 |
| 统计 | 预热后独立 A/B 多轮，建议至少 5 次并报告中位数与离散程度；不并行跑竞争内存带宽的基准 |

现有记录指出批次波动约 5–8%，单次几个百分点不能直接宣称有效提升。CPU 与 GPU、FP32 与 Q4、冷启动与热缓存应各自明确标注。速度结论最终应来自同条件测量；本文只给出值得优先验证的路径。
